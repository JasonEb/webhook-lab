# Plan Deviations

Running log of where actual implementation diverged from `implementation_plan.md` (the master plan) — different from `bug_log.md`, which tracks defects. A deviation here isn't necessarily a bug: it can be a design assumption that turned out wrong, a concrete choice made where the master plan explicitly left one open, an interface that had to change between phases, or API surface used that the master plan/`architecture.md` didn't originally know about. Where a deviation *was also* a bug, it's cross-referenced to `bug_log.md` rather than re-described.

## Log

| # | Phase | Area | What the master plan said/assumed | What actually happened | Why / impact |
|---|---|---|---|---|---|
| V1 | 0 | Subscription creation | Phase 0's task list says "Create a beta webhook subscription (`POST /webhooks`...)" — written as if the API call is simply the method. | First attempt went through the Quo dashboard's "Create a webhook" form, which turned out to create a **legacy**-format webhook (confirmed by an empty `GET /webhooks` beta-list result and an `openphone-signature` header on a test delivery). Had to switch to a direct `POST /webhooks` API call. | The dashboard has no visible beta-access toggle — the beta webhooks API appears to be API-only right now, a fact the master plan had no way to know in advance. Documented in `phase_0_summary.md`. |
| V2 | 2 | D2 dedupe key | `architecture.md` D2 and `implementation_plan.md` both frame the dedupe key as "`webhook-id`," with E1 testing whether "the id" is stable across retries — implicitly treating it as one identifier. | The real API revealed **two distinct identifiers**: a delivery-level `id` (equals the `webhook-id`/`svix-id` HTTP header) and the payload's own `id` field (which Quo's delivery-list API calls `eventId`). The implementation dedupes on the payload's `id`, not literally the header. | Both turned out stable across a retry, so no functional harm — but the master plan's mental model of "one id" was incomplete. See `architecture.md` section 2 ("Delivery `id` vs payload `id`") and `bug_log.md` is *not* involved here (nothing was broken, a concept was clarified). |
| V3 | 2 | API surface | `architecture.md`'s original citations (from a third-party write-up) didn't mention an update endpoint, and guessed delivery-detail fields (`responseDurationMs`, `triggerType`) that don't exist. The retry endpoint's path parameter was assumed to be named `:eventId`. | Used `PATCH /webhooks/{webhookId}` (not previously documented) to repoint subscriptions between phases without recreating them. Corrected the delivery-detail field list to what `GET /webhooks/{webhookId}/events` actually returns. Corrected the retry endpoint's path parameter to `deliveryId`. | The master plan's source material (quickstart + third-party write-up) was incomplete/slightly wrong on the API surface. All three corrections are in `architecture.md` section 2. |
| V4 | 2→3 | `DeliveryStore` interface shape | `architecture.md` D3 says "storage code behind a small interface so a Postgres swap stays contained" — doesn't specify whether stores own their own connection. Phase 2 shipped `openDeliveryStore(path: string)`, opening its own connection internally. | Phase 3 needed `DeliveryStore` and the new `DomainStore` to share one connection (required for `:memory:` test databases, and for `claim()`'s transactional semantics to matter). Changed the signature to `openDeliveryStore(db: Database.Database)` — a breaking change to code shipped one phase earlier. | Anticipated and flagged in `phase_3_implementation_plan.md` section 3.5a before writing the code, not discovered as a surprise. Low-risk since the only call sites were `server.ts` and tests. |
| V5 | 3 | Worker dispatch design | `phase_3_implementation_plan.md`'s own sketch (section 3.4) had `runOnce(store, domainStore, config)` calling the real `dispatchHandler` via a hardcoded import. | Changed to `runOnce(store, dispatch, config)` with an injectable `Dispatch` function; `handlers/index.ts` exports `makeDispatchHandler(domainStore)` (a closure) instead. | The sketched design wasn't testable — the retry/poison/crash tests need a stub handler that fails predictably across calls, impossible with a hardcoded real-handler import. Found and fixed while writing the tests, before any test ran against the wrong design. |
| V6 | 3 | D10's "always use `data.resource.*`" rule | `architecture.md`'s D10 rule, as stated after Phase 2, was general: use the resource's own timestamp, never the top-level webhook `createdAt`. | `call.summary.completed` has **no resource-level timestamp at all** — the rule's premise doesn't hold for this one event type. Handler falls back to top-level `createdAt` specifically for this case, documented as an exception. | This *was* also a bug (P3 in `bug_log.md` — the code guessed a nonexistent field and dead-lettered real events) — logged there for the defect, logged here for the rule change it forced in `architecture.md`. |
| V7 | 0–1 | Tech stack pin | `architecture.md` section 11 says "TypeScript (strict)" with no version constraint. | Had to pin `typescript` to `^5.9.3` rather than the newly-default TS 7 (the native-compiler rewrite), because `typescript-eslint` doesn't support TS 7 yet. | Ecosystem lag at the time of this project, not a design choice. Also logged as T1 in `bug_log.md` (tooling category). |
| V8 | 4 (planned) | `FAULT_MODE` capability | `architecture.md` 4.4 and `implementation_plan.md`'s Phase 4 experiment table define exactly two modes: `fail_first:N`, `slow:MS`. E4 ("which status codes are retried") needs to force arbitrary codes (400/401/404/410/429/500/503/3xx). | Planned a third variant, `status:CODE:N`, same counting mechanism as `fail_first` but with a configurable response code. | **Found while writing `phase_4_implementation_plan.md`, before any code existed — not yet implemented.** The master plan's experiment table assumes a capability the originally-scoped `FAULT_MODE` can't provide; without this, E4 isn't runnable at all. |
| V9 | 4 (planned) | `arrivals` table schema | `architecture.md` section 5's documented schema: `arrivals(id, webhook_id, event_type, received_at, ts_header, outcome)`. Section 4.6 says the analyzer should aggregate results "per fault scenario" — not possible from those columns alone once more than one experiment has run against the same table. | Planned a nullable `label` column, added beyond the documented schema, so each experiment run can be tagged and the analyzer can filter/aggregate per label. | **Found while writing `phase_4_implementation_plan.md`, before any code existed — not yet implemented.** The documented schema can't fulfill a requirement `architecture.md` itself states (4.6); the addition closes that gap rather than contradicting the schema's intent. |
